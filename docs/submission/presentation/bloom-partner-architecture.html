Everything Bloom runs is on one Boat.dev VM: nginx serves both Flutter Web apps and proxies /api to the FastAPI server, which is internal only. The server is the only component that talks to the outside: AI calls go to TrustedRouter, which forwards to GLM-5.3 Flash under a privacy floor; guideline searches go to Context.dev. The browser never sees a key and never chooses the privacy mode. Figma is upstream of the code: its tokens become the bloom_ui package both apps use.

Boat.dev

The computer Bloom is built on and served from: one VM runs the whole stack, and a frozen fork serves the demo.

Requirement 1

docker-compose.yml

1

Docker Compose on one VM

nginx serves both Flutter apps and proxies /api to an internal FastAPI container; SQLite sits on a volume.

2

Public HTTPS host on port 80

boat host … --public exposes the VM; nginx listens on IPv4 and IPv6 for Boat’s IPv6 address.

3

One-command deploy with checks

deploy.sh builds, waits for a healthy API, confirms the database is on the volume and runs 25 smoke checks.

4

boat fork for the demo

A frozen copy with --no-auto-stop serves judging, while the original VM keeps a snapshot as backup.

Boat.dev is the only place Bloom runs. The API is never exposed directly; only nginx is public. The demo fork is a frozen snapshot of a passing build, so last-minute changes can't break the judged copy. The original VM stays as a backup with the bloom-demo snapshot.

Partner 2 · Private inference

NY Token Exchange TrustedRouter

The only path from Bloom to a model. The server sets the privacy floor; the browser never can.

Requirements 2 and 3

server/app/router.py
server/app/attestation.py
apps/clinic · D03 panel

1

OpenAI-compatible gateway

The OpenAI SDK points at api.trustedrouter.com/v1, so one client handles every intake turn and brief.

2

Privacy floor on every request

provider = {min_privacy: zdr or confidential, allow_fallbacks: false}, chosen by BLOOM_MODE on the server.

3

Signed receipts and request IDs

Bloom asks for x-inference-receipt and stores the receipt, route, request ID and latency per call.

4

Shown to the clinician (D03)

The Privacy & Trust panel lists each call. The receipt is shown, but Bloom doesn’t verify its signature.

TrustedRouter is how requirement 2 (privacy floor) and requirement 3 (per-call evidence) are met. A TrustEvent row is stored for every model or retrieval call: metadata only, never clinical text. Be honest about the limit: Bloom displays the gateway’s signed receipt but does not verify the signature itself.

Bloom · Partner architecture

TrustedRouter in practice

If it can’t be private, Bloom says no

Dev mode · the live demo

Zero-data-retention route

z-ai/glm-5.3-flash with min_privacy = zdr (operator-declared). One retry on 429, 503 or 529, same model, after 2 s. D03 labels it ZDR, not confidential.

Private mode

Confidential route or nothing

min_privacy = confidential, no fallbacks, no retries. With no confidential model configured, every AI call returns 502 confidential_route_unavailable and nothing is sent anywhere else.

Negative test · D05

Proof on demand

The clinic asks for a confidential floor on a provider that is only ZDR. TrustedRouter answers HTTP 400 “No route candidates match”; D05 shows Refused after exactly one call.

Tests assert that a refusal is never followed by a second model call, and that a provider 5xx shows as an error, not a refusal.

This is the heart of requirement 2. Private mode fails closed by design: today PRIVATE_MODEL_ID is empty because NYTE has not named a confidential route, so private mode refuses everything. The demo runs in dev mode, and the UI says so plainly. The D05 negative test shows the refusal path live.

Partner 3 · The model

GLM-5.3 Flash · LetsEncrypt.AI

The model behind every AI call: each intake question and each physician brief, always through TrustedRouter.

Requirement 4

server/app/graph.py
server/app/prompts.py
TR_MODEL_ID in config.py

1

Structured intake in JSON mode

response_format json_object, temperature 0.2, low reasoning effort; prior turns are sent back as JSON.

2

Repair, then a safe fallback

Bad JSON gets one repair call, then a fixed next question, so the patient never hits a dead end.

3

Briefs that cite only what was found

The model drafts from retrieved passages; sanitize_brief drops any citation that was not retrieved.

4

Every output is a draft

Model, route, prompt version and evidence are stored as provenance; the clinician confirms, edits or rejects.

Before the JSON-mode fix, 6 of 8 turns in scenario S1 failed because the model answered in prose. After JSON mode, prompt changes and the repair step, live runs of S1, S3 and S7 got valid JSON on the first pass every time. If the model is unavailable, a deterministic brief is written and clearly labelled “written without AI”.

Bloom · Partner architecture

Partner 4 · Cited guidelines

Context.dev

Finds the guideline passages a brief may cite, without ever seeing what the patient typed.

Requirement 5

server/app/deidentify.py
server/app/retrieve.py
server/app/monitor.py

1

De-identified queries only

Built from structured fields, such as “cervical cancer screening interval age 30-39”; a planted-identifier test guards it.

2

Allowlisted guideline sites

Web search with includeDomains for ACOG, USPSTF and CDC, plus a second host check on every result.

3

Evidence stored and cached

Passage, URL and retrieval time are saved per brief and cached per query, so demos don’t spend credits.

4

Monitor webhook (stretch)

An HMAC-signed webhook can flag “guideline updated” on a brief; it’s off until a secret is set.

Context.dev satisfies requirement 5. The key design choice is that the search query is built from structured intake fields (age band, topic), never from free text, so no identifier can leak into a third-party search. The brief may cite only passages that were actually retrieved and stored. With no passage, D02 shows “No guideline retrieved”.

Partner 5 · Design source of truth

Figma

Every screen is designed first in Figma; its tokens and components become the shared Flutter design system.

Requirement 8

docs/design-tokens.json
docs/02-app-flow.md
packages/bloom_ui

1

Screen ID = frame name = route

A01, P01–P04, D01–D06 and S01 are Figma frames and go_router route names, with node IDs in the screen index.

2

Tokens exported to code

16 primitives, 19 semantic colours, 10 dimensions and 8 text styles (Fraunces, DM Sans) feed bloom_ui.

3

Shared components

Button, StatusChip, ChatBubble, QuickReply, Banner, CitationLink, TrustRow and DecisionBar.

Loading, generating, refused, model error, urgent, edited and rejected states exist as frames.

The rule in this repo is: a design change goes into Figma first, then the docs, then the code. Bloom tokens are mapped into a Material 3 ColorScheme in bloom_ui, so both Flutter apps share one look. This palette (plum, warm canvas, verified green, critical red) is the one used in this deck.

Bloom · Partner architecture

How it was built

Planned in gates, built by agents, coordinated in the open

Claude Code

Eight scoped agent briefs

Router, safety, retrieval, Flutter foundation, graph and API, patient UI, clinic UI and deploy, each with its own prompt in docs/agent-prompts/.

Approval gates

G1 to G4 before release

Design, technical design and implementation plan were approved before any code; the G4 release check records tests and open fixes.

Teamily · Boat.dev

Daily status, coding aboard

Status posts and sponsor questions went to the Teamily group; boat ssh and boat prompt let work continue on the VM itself.

The team worked in hackathon-fast mode: one plan document stood in for the full doc set, and three compressed gates were approved on 16 November before code started. Each part of the system was built by a Claude Code agent from a written brief, which is why the code maps so cleanly onto the partner boundaries.
